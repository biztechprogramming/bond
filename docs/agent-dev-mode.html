Agent Dev Mode — what's changing

Keep the Docker isolation for agents, but stop letting it tax the edit loop. The change makes the orchestrator run natively in development and lets agent containers run your local working tree directly — so iterating no longer means commit → push → re-clone.

branch: feat/agent-dev-mode 5 files changed · gated behind dev flags production path untouched

0The one-sentence version

Today, to test any Bond code change inside an agent you must commit → push → restart (the agent re-clones from origin on every start). Dev mode replaces that with edit → reload by bind-mounting your host repo into the agent and skipping the git reset — without removing isolation, because it's the agents that stay containerized, not your editor.

1Where the isolation boundary moves

The difficulty was never "Docker." It was that the orchestrator itself ran inside a container and drove Docker through the host socket — forcing a whole layer of path-mirroring hacks. Dev mode runs the orchestrator natively; only agents stay isolated.

Before containerized orchestrator

bond-bond runs in a container and reaches the host Docker daemon via a mounted socket. Needs $HOME:$HOME path-mirroring + BOND_HOST_HOME translation so bind-mount paths resolve on the host.

Host machine
bond-bond container
backend + gateway + frontend · mounts /var/run/docker.sock, $HOME:$HOME:ro
│ docker.sock + path translation ▼
agent container
/bond = per-agent clone, reset to origin on start
containerized

After (dev) native orchestrator

bond-bond runs on the host with direct Docker access. The socket-mount + path-mirroring layer simply goes dormant (no code deleted). Agents still containerized.

Host machine
bond-bond (native process)
make dev-mounted · uvicorn --reload · direct docker access
│ docker run · mounts your real repo ▼
agent container
/bond = live bind-mount of host working tree
native agent (isolated)
Isolation preserved
The agent is still a separate container with its own memory/CPU limits, network, and credentials. What changed is how its copy of the Bond source arrives — and that the orchestrator no longer needs to live in a box itself.

2The core change: how code reaches the agent

This is the single biggest friction-killer. Same container, different mount.

Before re-clone from origin

# adapters.py — non-deploy agent
bond_volume = "bond-clone-<agent_id>"
docker volume create $bond_volume
-v $bond_volume:/bond:rw

# agent-entrypoint.sh, every start:
git fetch origin
git reset --hard origin/$branch

Your local edits are invisible to the agent. Only what's pushed to origin exists inside.

After (dev) mount the host tree

# adapters.py — when BOND_DEV_MOUNT_SOURCE=1
-v $PROJECT_ROOT:/bond:rw
-e BOND_DEV_SKIP_GIT=1

# agent-entrypoint.sh:
if [ "$BOND_DEV_SKIP_GIT" = "1" ]; then
  # skip clone/fetch/reset entirely
fi

/bond is your working tree. The skip-git guard is what stops reset --hard from wiping your uncommitted edits.

Shared tree caveat
In dev-mounted mode all agents share one working tree (your repo). Great for iterating; it means it is not the mode for testing per-agent branch isolation. Unset the flag to get back independent per-agent clones.

7The piece still to build

Bond's frontend exposes per-agent Pull / Branch-switch / Reload controls (Design Doc 116). They assume /bond is a throwaway clone. Against your mounted working tree they misbehave:

ControlWorker actionIn dev-mounted mode
Pullgit reset --hard origin/<branch>Destroys your uncommitted edits across the shared treegate off
Branch switchgit checkout <branch>Switches your working branch for every agent at oncegate off
Reloadcheckout → os.execvThe re-exec is what you want; the checkout step must be skippedno-git path
Proposed fix
When an agent is in dev-mounted mode, collapse the UI to a single safe "Reload code" button (pure os.execv, no git) and hide Pull / Branch-switch. ~3 touch points: a dev flag on the worker /branch status, a no-git path in /reload, and conditional rendering in ConversationInfoPanel.tsx.
