Bond — Architecture Review

Current state, what's actually running, where the complexity comes from, and a path to simpler. Snapshot taken 2026-04-30.

Why this exists: Concern that containerizing the bond service and adding a host-side daemon introduced complexity that may not be earning its keep — especially for single-machine solo use. This doc audits what's actually running vs. what the code can run, and lays out three viable architectures.

1. The Headline Findings

What's actually running

  • container bond-bond-1 — single container running three processes: backend (uvicorn), gateway (tsx watch), frontend (pnpm)
  • container bond-spacetimedb — database
  • optional bond-langfuse-* — six containers, observability stack
  • missing bond host daemon (port 18795) — env var points to it, but nothing is listening

Surprises in the audit

  • The "gateway in a container" worry: gateway is not a separate container — it's a process inside bond-bond-1 alongside backend & frontend.
  • The host daemon (bond_host_daemon.py) exists in code but is not deployed. Agent containers are spawned via the docker socket mounted into bond-bond-1, not via the daemon.
  • The clone failure you hit is a credential-passthrough bug: bond-bond-1 has no SSH key mounted, so when it spawns an agent container it can't pass one through.

5. Why Each Layer Exists

Gateway as a separate process

Real reason it exists: Python is poor at long-lived multiplexed SSE/WS connections; Node excels at it. The gateway holds open connections to the browser and to each running agent, and routes events. Backend stays focused on REST orchestration.

Cost: One more language runtime to manage. Mostly invisible because it shares a container with the backend today.

Putting backend + gateway + frontend in one container

Real reason: Reproducible setup. Anyone running docker compose up gets a known-good environment without installing pnpm + uv + node + python locally. Docs/onboarding becomes trivial.

Cost: Three processes share one container's lifecycle. Path.home() inside it is /home/bond, not your real home — so any code that auto-discovers SSH keys, Claude config, etc. silently misses them. This is the root cause of the clone failure. The fix is design doc 112 (credential passthrough) — partially built, not fully wired.

Host daemon ("faucet")

Real reason: Two future capabilities: (1) bond on machine A spawning agents on machine B (design doc 089 — remote container hosts), and (2) browsing the host's filesystem from the bond UI when bond itself is in a container (design doc 112). The daemon is a thin REST shim around docker + filesystem.

Cost today: Zero — it's not running. Cost tomorrow: One more service to install/start/monitor per host. It's only earning its keep in scenarios you don't currently have.

6. Three Viable Architectures

Option A — Native single-host (simplest, "before")

Backend, gateway, frontend run as host processes. SpacetimeDB stays in a container (it's a binary you don't want on host). Agent containers spawned via host docker. No host daemon. ~/.ssh just works.

Pros: Fewest moving parts. Credentials work out of the box. Edits to backend code don't require a rebuild — uvicorn's reload sees them. Cons: Onboarding requires installing the right runtimes.

Option B — Containerized single-host (current)

All three bond processes in one container, mounting docker.sock to spawn agents. The host daemon is defined but not running. Credential passthrough is the recurring tax.

Pros: One-command setup. Same container shape on dev and prod. Cons: Credential discipline (Path.home() trap), agents born blind to your SSH keys unless 112 is fully wired. Backend code changes require a container rebuild or volume-mounted source.

Option C — Multi-host scaled-out

Bond runs anywhere; each worker host runs a host daemon at :18795; bond calls daemons over HTTP/SSH tunnel. Agents are git-cloned on the remote host instead of bind-mounted. Designed for: shared bond instance, multiple GPU/CPU pools.

8. Specific Recommendations

For your immediate "fix the clone" problem: two viable fixes, smallest first.
  1. Switch the agent's clone URL to HTTPS. The bond repo is public (git ls-remote works without auth). One-line change in backend/app/sandbox/adapters.py:278 and scripts/agent-entrypoint.sh:28. No SSH plumbing needed. Pushes from agents would still need a token via GITHUB_TOKEN (already exported from vault).
  2. Wire credential passthrough properly (Doc 112). Mount ~/.ssh:/home/bond/.ssh:ro into bond-bond-1, make sure local adapter sees it, propagate to agent containers via /tmp/.ssh as the entrypoint expects. Bigger change but unlocks SSH-based pushes from agents.
For your bigger "is this too complex" question:
  • The host daemon is aspirational right now. It's not running, not earning its keep. Don't feel obligated to make it work — defer until you actually need multi-host scale.
  • Containerizing bond was the choice that introduced credential passthrough. If you regret it, dropping back to native processes for backend/gateway/frontend (Option A) eliminates an entire class of problems and is a 1–2 hour change.
  • If you keep bond containerized (Option B), finish Doc 112. Half-built credential passthrough is worse than either fully native or fully wired — silent failures (clone, token, claude config) are hard to debug.
  • Agents staying in containers is non-negotiable — that isolation is the point. The question is only where the bond orchestrator lives.

9. The Path I'd Take

  1. Today: Switch agent clone URL to HTTPS (5-min change, fixes the immediate breakage). Capture the SSH-key route as a known follow-up if/when agents need to push.
  2. This week: Decide between Option A (revert bond to native) and Option B (finish containerized). The decision driver is: do you onboard others to this stack often? If yes, Option B + finish Doc 112. If no, Option A is materially simpler.
  3. Defer: Host daemon. Don't deploy it until either (a) you containerize bond and need host filesystem browsing in the UI, or (b) you actually want multi-host execution. The code can stay in the repo as a future feature.
  4. Cleanup: Remove or gate the BOND_HOST_DAEMON_URL env var so it isn't quietly pointing at a service that doesn't exist — that's a debugging trap.
